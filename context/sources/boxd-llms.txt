# boxd

> Composable computers for devs and agents. Real hardware-isolated Linux VMs in the cloud: compose one, then spin up as many as you need.

boxd gives developers and AI agents their own persistent Linux machines, reachable over SSH and HTTPS.

You use boxd through the `boxd` CLI (`--json` gives machine-readable output), the Python SDK (`pip install boxd`) and the TypeScript SDK (`npm install @boxd-sh/sdk`), SSH into any machine, each machine's own HTTPS URL, and the web console at https://app.boxd.sh. A person signs in once in the browser; scripts, CI and servers use an API key.

## Quick start

### 1. Install the CLI

```
curl -fsSL https://boxd.sh/downloads/install.sh | sh -s -- --yes
```

On Windows, in PowerShell:

```
& ([scriptblock]::Create((irm https://boxd.sh/downloads/install.ps1))) -Yes
```

`--yes` (`-Yes` on Windows) also installs the boxd agent skills (Claude Code, Codex, Cursor, Copilot, Gemini CLI, OpenCode), the PATH line and, outside Windows, shell completions. Without it, the installer asks in a terminal, and installs only the binary when there is no terminal to ask on.

The PATH line only reaches new shells. In the shell you are in, run `export PATH="$HOME/.local/bin:$PATH"` first, or call `~/.local/bin/boxd`. On Windows the installer adds `~\.local\bin` to your user PATH, which reaches new terminals and the PowerShell that ran it.

### 2. Sign in: your user does this

Signing in is a person's step. If you are an AI agent, ask your user to run this in their own terminal:

```
boxd auth login
```

It opens a browser (or prints a link) where they sign in with GitHub or Google; a new account is created the same way. A new organization also needs a payment method before its first machine: right after sign-in they are asked to connect one (nothing is charged, and the free credits arrive with it). The command gives up after 5 minutes without a sign-in, and waits up to 10 more for the payment step. Wait until your user says it's done before running other boxd commands: any boxd command that needs an account starts this same sign-in.

Don't start it yourself unless your user asks you to or can't reach a terminal on this computer. In that case, start it and give them the link it prints, saying what it is for. Run it in the background with its output in a file, because it waits for them. `setsid` keeps it alive in agent tools that stop a command's background processes when the command returns (macOS has no `setsid`; leave it out there):

```
setsid nohup boxd auth login > /tmp/boxd-login.log 2>&1 < /dev/null &
sleep 3; cat /tmp/boxd-login.log
```

Leave it running and don't start a second one: the link signs in only the command that printed it. Without a person to sign in, use an API key (below).

### 3. Create a machine and use it

```
boxd machine new my-app
boxd machine exec my-app -- uname -a
ssh my-app.boxd
```

Machine names are unique across all of boxd (each one is also `<name>.boxd.sh`), so `my-app` may already be taken: pick a name nobody else is likely to use, or leave it out and boxd generates one and prints it.

## Programmatic access with an API key

For CI, scripts, servers and agents that run without a browser, use an API key instead of signing in on that computer. A key acts as you, inside one organization.

### Create a key

A person creates it once, either in the console at https://app.boxd.sh/keys or with the CLI on a computer where they are signed in:

```
boxd auth keys create my-ci
boxd auth keys create my-ci --expires-in-secs 2592000   # expires in 30 days
```

The key (`bxd_...`) is shown only once, so store it right away, for example as a CI secret. `--json` prints it as `{"api_key": ...}`. A key works in the organization you are in when you create it; `--org <name>` picks another.

### Use it from the CLI: BOXD_TOKEN

```
export BOXD_TOKEN=bxd_...
boxd machine new my-app
boxd machine exec my-app -- uname -a
boxd machine cp ./build.tar.gz my-app:build.tar.gz
```

`--token <key>` does the same for one command. The CLI does not read `BOXD_API_KEY`: with no key in `BOXD_TOKEN`, it starts the browser sign-in instead and waits for it, which in CI means a 5-minute hang. In GitHub Actions, store the key as a secret and map it for the CLI:

```
env:
  BOXD_TOKEN: ${{ secrets.BOXD_API_KEY }}
```

### Use it from the SDKs: BOXD_API_KEY

The Python and TypeScript SDKs read the key from `BOXD_API_KEY` (or take it as `api_key=` / `apiKey`). They accept it in `BOXD_TOKEN` too, which wins if both are set, so a job that uses both the CLI and an SDK can set just `BOXD_TOKEN`.

```
pip install boxd              # Python
npm install @boxd-sh/sdk      # TypeScript
export BOXD_API_KEY=bxd_...   # from https://app.boxd.sh/keys or `boxd auth keys create`
```

If you are writing this code for someone who has no key yet, tell them where to create one: https://app.boxd.sh/keys, or `boxd auth keys create` on a computer where they are signed in.

```python
from boxd import Boxd

boxd = Boxd()  # reads BOXD_API_KEY
machine = boxd.machines.create("my-app")
boxd.machines.wait_until_ready(machine.id)
print(boxd.machines.exec(machine.id, "uname -a").stdout)
```

### What a key can't do

`ssh <name>.boxd` needs `boxd auth login` on that computer: only an interactive sign-in links an SSH key, so with an API key the CLI writes no SSH alias. Use `boxd machine exec` and `boxd machine cp` instead. List keys with `boxd auth keys list` and delete one with `boxd auth keys remove <name>`.

## Compare

How boxd compares with other agent sandboxes. Each page opens with an at-a-glance table (where boxd is ahead, where the other product is), then when to pick which, then a sourced, dated feature matrix. Every /compare/ page is also served as Markdown at index.md next to it.

- https://boxd.sh/compare — boxd against E2B, Daytona, Modal, Vercel Sandbox, Blaxel and Cloudflare Sandbox: full VMs, a composable kit, apps that answer from sleep, agents built in, and only active vCPU billed. Sourced and dated, with measured numbers.
- https://boxd.sh/compare/e2b (Markdown: https://boxd.sh/compare/e2b.md) — E2B runs short-lived sandboxes from an SDK, with a time limit on every run. A boxd machine is a full computer that stays, wakes on a request with your app still running, and comes with coding agents installed. It bills only active vCPU, where E2B bills every vCPU it provisions.
- https://boxd.sh/compare/daytona (Markdown: https://boxd.sh/compare/daytona.md) — A Daytona sandbox is a container unless you pick its VM class. Every boxd machine is a full VM with its own kernel, starts at 2 vCPU and 8 GiB, and keeps your app running while it sleeps. It bills only active vCPU, where Daytona bills the vCPUs a sandbox reserves.
- https://boxd.sh/compare/modal (Markdown: https://boxd.sh/compare/modal.md) — Modal sandboxes are short-lived, end after 24 hours at most, and can't be stopped and started again. A boxd machine stays until you delete it and sleeps with your app running. It bills only active vCPU, where a Modal sandbox pays for at least the cores it requests.
- https://boxd.sh/compare/vercel-sandbox (Markdown: https://boxd.sh/compare/vercel-sandbox.md) — Vercel Sandbox runs sessions of up to 24 hours and brings back the disk, not the running processes. A boxd machine keeps its memory while it sleeps, so your app is still running when a request wakes it. Both bill only active CPU, and boxd's rate is well under half of Vercel's.
- https://boxd.sh/compare/blaxel (Markdown: https://boxd.sh/compare/blaxel.md) — Blaxel sandboxes suspend within seconds and resume fast, with the filesystem held in memory. A boxd machine is a full computer with a 100 GB disk, plain SSH and coding agents installed, and it bills active vCPU and memory in use rather than allocated memory.
- https://boxd.sh/compare/cloudflare-sandbox (Markdown: https://boxd.sh/compare/cloudflare-sandbox.md) — Cloudflare Sandbox gives your Worker a container on the edge, with a disk that's wiped when it stops. A boxd machine is a persistent VM with its own disk, SSH and URL, that you can use without writing a Worker. Both bill only active vCPU, at a lower rate on boxd, and boxd bills memory in use rather than provisioned.
- https://boxd.sh/blog/boxd-vs-exe-dev (Markdown: https://boxd.sh/blog/boxd-vs-exe-dev.md) — boxd and exe.dev both give you a persistent Linux VM over SSH. Where each is better: regions, self-hosting, pausing with memory, SDKs and egress control.
- https://boxd.sh/blog/boxd-vs-sprites (Markdown: https://boxd.sh/blog/boxd-vs-sprites.md) — Sprites and boxd agree on the architecture: persistent microVMs are the right primitive for AI agents. Where the two implementations diverge, honestly.

Measured on boxd's production cluster (Frankfurt), 2026-10-29, from a client in the same datacenter:
- A hibernated machine answered an HTTPS request with its app still running in 156 ms median (104–213 ms, n=10).
- A new machine created from a snapshot answered its first HTTPS request 1.19 s after the create command (median, 1.14–1.24 s, n=10).
- CPU: 12.6 runs/s on the Node.js web tooling test at 4 vCPU (StarSling's open sandbox benchmark; other providers: https://github.com/starslingdev/hpc-sandbox-benchmarks/blob/main/LEADERBOARD.md).
- Method: https://boxd.sh/compare/#how-we-measured

## Key features

- Persistent state: Files, packages, databases, running processes — all survive disconnects, reboots, and time. Your agent stops at 2am, picks up at 9am.
- Instant forking: Fork a full machine — memory, disk, processes — in under 200ms. Branch to explore approaches in parallel, keep the winner.
- Scriptable interface: Drive everything from the `boxd` CLI, with `--json` on every command for scripts and agents. No dashboard, no heavyweight SDK.
- Always on: Machines keep running after you disconnect. Long builds, background jobs, agent tasks all continue.
- Automatic HTTPS URLs: Every machine gets a public URL automatically. Certificates and DNS handled.
- KVM isolation: Every machine runs its own kernel — real hardware-level isolation, not containers. Safe for untrusted, agent-generated code.
- Pause to zero: Machines sleep when idle and pay only for their disk while they're off. Resume in sub-millisecond.
- Self-hostable: Run boxd on your own infrastructure, any KVM-capable server. EU hosting by default. No vendor lock-in.

## Specs

- Ubuntu 24.04 (full, unminimized, with man pages and systemd)

- Cold boot: <10ms
- Resume from sleep: instant (sub-millisecond)
- Fork time: <200ms

## Standby and hibernation

- A machine goes to standby or hibernates after its timeout passes with no network traffic in either direction, so a process that calls out every few minutes keeps it awake. CPU work, disk work and local timers don't count, and the machine's own DNS, NTP and DHCP traffic is ignored. With `idle.ignore-outbound` on, only connections opened to the machine count.
- A hibernated machine wakes only on a new connection through boxd (HTTPS or SSH, including over the org's tailnet, or `boxd machine exec`), not on a raw exposed port and not on its own cron jobs.
- `boxd machine get my-app` shows the timeouts; 0 (shown as `off`) means it never sleeps.

## Pricing

- Credit-based, billed in euros or US dollars (an organization's currency is set when it is created). You only pay for active vCPU, not for the vCPUs a machine reserves: on average only 10% of a machine's reserved vCPU is active. RAM bills on memory in use and disk on what you have written to, never on provisioned size. Metered every second, settled every 15 minutes, no minimum charge per machine.
- vCPU: EUR 0.039 / USD 0.047 per vCPU-hour, on active vCPU only (not the vCPUs the machine reserves): a 2 vCPU machine that is active 10% of an hour pays for 0.2 vCPU-hours.
- RAM: EUR 0.012 / USD 0.014 per GiB-hour, on memory actually resident (not the provisioned 8 GiB), while running or in standby.
- Disk: EUR 0.00008 / USD 0.000096 per GiB-hour, on disk written to (not the provisioned 100 GiB), in every state. Hibernated machines pay for disk only.
- A default machine (2 vCPU / 8 GiB) is about EUR 0.17 / USD 0.21 per hour with every vCPU active and full memory while it runs, and about EUR 0.03 / USD 0.04 per hour with 0.2 vCPU active and holding 2 GiB with 20 GiB written to disk.
- Every account is an organization: shared machines, one credit balance, 100 machines included.
- EUR 30 / USD 30 free credits for new accounts, granted when a payment method is added.
- Custom: bigger machines, higher quotas, volume pricing, or self-host/BYOC on your own hardware. For companies of any size. Contact us.

## Architecture

Our own custom VMM, in Rust, built on KVM. No Docker, no external dependencies. Raft consensus for coordination. Hosted in Frankfurt and New York.
